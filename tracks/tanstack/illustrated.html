Next に向けられる不満は、箱の内側

採用される理由と、文句の理由は同じ場所です。枠が HTML を組み立てる仕事を引き受けるからです。

1. キャッシュが先に決まる

App Router 初期は fetch をキャッシュする側に寄せた。Data Cache、Full Route Cache、Router Cache が合成され、「なぜ古い HTML が出るか」が追いにくい。Next.js 15 は公式にデフォルトをキャッシュしない側へ変更した。デフォルトを変えるほど、暗黙は現場のコストだった、という記録です。

2. サーバーとクライアントがファイルの属性になる

React Server Components ではデフォルトがサーバー、'use client' でクライアント。日付や関数は props で渡せない。これは React のモデルですが、Next はアプリの標準経路にしました。インタラクティブな画面ほど、「このファイルはどっちで HTML を出すか」が先に来ます。

3. URL の型が後回し

下の「Router と href」を見てください。href は文字列、searchParams は自分で削る。フィルタが URL に乗るダッシュボードほど、ここがバグになります。

4. 二つの書き方と、ホストとの距離

Pages Router と App Router が長く並んだ。コードは OSS で自前ホストもできる一方、開発の主導は Vercel にあり、画像などの厚さは載せ先で違います。陰謀ではなくインセンティブの話として出ます。

Query と fetch は、効く時刻が違う

どちらも posts の JSON を取ります。だから競合に見えます。HTML がいつ確定するかが違います。

Next 15 以降、fetch はデフォルトでキャッシュしません。長く持たせるなら枠のキャッシュ API を明示します。

TanStack Query

ブラウザに残ったあと、同じキーのデータを共有・再取得する。

queryKey: ['posts']
staleTime: 60_000

staleTime は「この HTML を何ミリ秒新鮮とみなすか」が名前として残ります。サイドバーの開閉は useState のままです。

同じリンクでも、HTML の href の出どころが違う

ブラウザが見るのはどちらも <a href> です。違うのは、その文字列を誰が保証するかです。

Next.js

/posts/123/edit

ファイル名がルートです。app/posts/[postId]/page.tsx。Typed Routes でパスは寄せられます。search はまだ string | string[] | undefined を自分で削ることが多いです。

TanStack Router

/posts/$postId/edit

ファイルから route tree が生成され、to と params が型を持ちます。validateSearch で ?page=2 もルートの契約になります。

Start は、引き出しを足す枠

Router までなら Vite の CSR でも足ります。足りないのは、最初のドキュメントをサーバーが組むことと、サーバーだけの秘密です。Start は Router のタグを置き換えません。SSR と createServerFn を被せます。執筆時点は Release Candidate です。

層を戻す

  • Query だけ — Next のままが普通。乗り換えではない。
  • Router — URL と search を契約にしたい。Vite SPA ならここで足りることがある。
  • Start — その Router に SSR が要るとき。Next と同層の選択。

コンテンツと事例と採用が速度になるなら、箱（Next）は今も合理です。同じセッションで URL とキャッシュを細かく動かすなら、引き出しが効きます。
