# なぜ Go か

## このレッスンでわかること

- Go が「速い動的言語」ではなく、静的型・コンパイル・goroutine の組み合わせであること
- サーバー用途で標準ライブラリが厚い、という意味
- Hono（JS の Web Standards）との対比。どちらが上位ではない

## 本文

Go は Google 発の言語で、仕様が小さい。サーバーを書く現場で繰り返し挙げられる性質はだいたいこの三つである。

1. **コンパイルして一つのバイナリになる**  
   Node のように実行マシンにランタイムと `node_modules` を揃える必要が、相対的に少ない。Docker の最終イメージを薄くしやすい（次トラック）。

2. **`net/http` が本体にある**  
   Hono に相当する「HTTP の最小」が、外部フレームワークなしで書ける。フレームワーク（chi、echo、gin など）は便利だが、導入の第一歩は標準で足りる。

3. **goroutine**  
   安価な並行の単位。`go f()` で関数を並行に走らせ、チャネルでやり取りする。Hono の 1 リクエスト 1 `Context` と同じく、「同時にたくさん待つ」がサーバーの普通の仕事である。詳細は予定レッスン。

TypeScript の構造的型とは違い、型は明示が多く、インタフェースは「メソッドセットを満たせば実装」である。最初は「関数と struct と `error` を返す」で読める。

### Hono との関係

同じ HTTP メッセージを扱う。違いは土台である。

- Hono: `Request` / `Response` / `fetch`。Workers から Node まで同じアプリコード
- Go: バイナリと OS のソケット。ランタイムは Go 自身。Edge の JS と同じコードは共有しない

「フロントも API も TypeScript で型を共有したい」なら Hono + oRPC が強い。「API だけ堅く・デプロイをバイナリにしたい」なら Go が強い。両方学ぶのは、層は同じで実装が違うと知るためである。

## 確認

- Go のプログラムを他マシンで動かすとき、相手に `node_modules` 相当が必要か（典型的なビルドの話）
- Hono を Go で置き換える対象は、React か HTTP サーバーか
- goroutine が欲しくなるサーバーの仕事を一つ挙げよ
